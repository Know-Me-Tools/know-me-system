PART I · 01 · PERSONAL OPTIMIZATION

Design teams around your bottleneck, not around an org chart.

Enterprise team design starts from headcount and reporting lines. A personal bench starts from the three scarce things a single operator actually has:

Scarce resource 1

Your attention

Every approval, clarification and review costs you minutes. Optimize for fewer, better-packaged decisions: batch approvals into the KnowMe inbox and morning brief; let standing grants cover routine effects.

Scarce resource 2

Context continuity

Your work is spread across Claude Code, Codex, Kimi, MiniMax, The Boss, OpenDesign and your phone. Optimize for resumability: durable state and shared memory so any tool can pick up where another stopped.

Scarce resource 3

Trust budget

You can only verify so much. Optimize for independent evidence: a maker never grades its own work; high-impact effects wait for fresh authority.

Every design decision below is scored against those three. A team that saves you an hour of typing but costs you two hours of reconciling contradictory outputs is a net loss. The KBD rule applies unchanged: use a single agent for a small, coherent task; add agents only when isolation, specialization, independent evaluation or real parallelism pays for the coordination.

PART I · 02 · TWO ALTITUDES

High-level: standing teams and cadences. Low-level: one bounded assignment.

Think at two altitudes and never mix them in one prompt.

High-level questions (answer once, revisit monthly)

  1. Which outcomes recur? Anything you do more than twice a month is a candidate for a standing role or a scheduled workflow. One-offs stay single-agent.
  2. Where do you lose context today? Tool switches, overnight gaps, phone vs desk. Those seams decide where shared memory and handoff packets are mandatory.
  3. Which judgments must be independent? Code review, factual claims in marketing, security, accessibility, financial numbers. Each gets a separate evaluator role — preferably a different model family.
  4. Which effects are routine vs high-impact? Routine (open an issue, draft a post, update docs) gets a standing grant. High-impact (publish, merge to main, spend, message customers) waits for you in KnowMe.
  5. What runs without you? Observers and cadences go to BossFang. Everything else is on-demand from a harness.

Low-level questions (answer per assignment)

An assignment is complete only when it carries every field the KBD definition contract lists. Use this as the literal brief template you paste into any harness or send as UAR run input:

# assignment.yaml — portable brief; adapt field names to the target runtime
assignment_id: km-site/change-12/task-3
role: web-ui-implementer          # accountability boundary, not a process
goal: "Implement the pricing section from DESIGN.md tokens"
why: "Launch page must convert Pro tier; see objective OBJ-7"
input_revision: 184                 # KBD runtime revision / git SHA you started from
owns: ["site/src/sections/pricing/**"]   # disjoint write ownership
reads: ["design-systems/knowme/DESIGN.md", "openspec/changes/pricing/**"]
skills: ["frontend-design", "scaffold-react-vite"]  # task-driven, not job-title-driven
model_policy: { tier: medium, model: "<concrete id from models-select>" }
budget: { attempts: 3, wall_clock_min: 40, max_usd: 2.00 }
external_actions: none              # proposal | scoped change | external action
return:
  - changed paths + digest
  - screenshots at 390/1024/1440, both themes
  - unresolved questions
stop_when: "acceptance criteria in tasks.md §3 pass OR budget exhausted → report BLOCKED"
reviewer: a11y-reviewer (fresh context, different model)

The rule that prevents most failures

Definitions are portable; identity, credentials and grants are not. Exporting a team to Codex or BossFang copies the definition. Each target mints its own instance with its own permissions — the manifest's owns field is a coordination agreement, never a filesystem permission.

PART I · 04 · THE ESCALATION LADDER

Climb only as far as the work demands.

Maker ≠ evaluator, bounded loops, and the determinism boundary

  • Maker and evaluator are separate assignments. The evaluator receives goal, constraints, exact artifact revision and evidence, and returns findings or PASS / CONTINUE / BLOCK — never a hidden repair. A repair is a new executor assignment followed by review of the new revision. In this stack: adversarial-review (judge ≠ producer via liter-llm kbd-judge/kbd-critic) and kbd-goal-check.
  • Every loop has a stop condition: acceptance condition, attempt/time/cost limits, blocker behaviour and a pause path. BossFang enforces this at the scheduler level with Loop{max_iterations, until}, [autonomous] max_iterations and [budget].
  • Agents propose; deterministic host logic admits. A model may say "this change is complete." The KBD runtime, UAR's governance gate or BossFang's approval queue decides whether that transition is valid for the current revision.
  • External actions are separate transactions. A journal entry does not atomically include a GitHub issue, a post or a deployment. Use action identity, bounded retries, receipts and reconciliation; record uncertain outcomes as uncertain.

Status caveats from source inspection

gap Inline Cedar is emitted by the compiler but no runtime consumer installs it; skill version/required/config collapse to preferred IDs during conversion; policies/default.cedar is permit-all. Treat authored governance as documentation until those are closed, and enforce with deployment-level Cedar files and approvals. gap UAR has no scheduler — recurring runs belong to BossFang.

Multi-agent inside one UAR run

The parent turn gets native tools: spawn_agent (artifact ID, delegated prompt, history full | last_turns), send_agent_message, wait_agents (≤ 60 s per wait), list_agents, interrupt_agent. Children run with intersected permissions and root-shared budgets — a child can never regain what the parent lost. Use this for supervisor/worker patterns inside a single request; use BossFang workflows or the team ledger for anything that must survive a restart.

Skills and memory in UAR

  • Skills load from $UAR_BUILTIN_SKILLS_DIR, ~/.uar/skills (WASM, WIT uar:skill@0.1.0) and — importantly — the standard ~/.agents/skills directory, scanned at startup. Install the Prometheus pack there once and UAR, Codex and Claude Code all see it.
  • Memory is opt-in (memory.enabled: true). Point it at the shared surreal-memory instead of an embedded DB so harness sessions and UAR agents read the same graph: UAR_MEMORY__SURREAL_ENDPOINT, or keep the in-process store and have clients use UAR_MEMORY_MCP_URL=http://127.0.0.1:1906/mcp/memory. Pick one authority per scope.

PART III · 11 · TRUE CONTEXT SHARING

Five layers, each with one job — and none of them is "paste the chat".

Context sharing fails when one layer is asked to do another's job: chat history as state, memory as authority, a skill as a permission. Keep them separate:

The switching protocol

This is the ritual that lets you walk away from Claude Code, open Codex (or Kimi, or your phone), and continue without re-explaining.

  1. Switch-out (source harness). Finish or checkpoint the current task. Run karpathy-progress-memory at the boundary (Claude Code does this via hooks; elsewhere call node scripts/record-progress.mjs --project-root "$PWD" --boundary task). Then agent-team-handoff → handoff-create with source owner, expected task revision and destination harness.
  2. Publish memory. memory-queue the decisions and facts worth recalling (scope team:<id> or project:<id>), commit state, then memory-publish. Unavailable service → it stays queued; nothing is lost.
  3. Stop the source. A state transfer does not stop the old process. Pause or close it so two harnesses never edit the same files.
  4. Switch-in (destination). Open the repo. The harness loads L1 (AGENTS.md) and L2 (skills). Ask it to run kbd-status (reads the waypoint and confirms the runtime revision) and kbd-memory-recall (surreal-memory → prior-context.md).
  5. Accept. Read the packet as task data, verify its evidence against the current revision, then handoff-accept with the destination role/harness. Only acceptance transfers ownership; a stale packet is reconciled, never replayed.
# paste as the first message in any harness (switch-in prompt)
Restore context before doing anything:
1. Read AGENTS.md and .agent-team/<team>/README.md.
2. Run kbd-status; report phase, change, task and runtime revision.
3. Run kbd-memory-recall for this project; summarize prior-context.md in 5 bullets.
4. Open the newest handoff packet in .agent-team/state.json; verify its git HEAD
   and evidence against the working tree. Report mismatches; do not proceed on stale state.
5. Accept the handoff as role <role> on harness <harness>, then continue the task.

PART IV · 12 · OPENDESIGN AS THE DESIGN ENGINE

One design daemon, reachable from every agent through MCP.

Choosing who runs the design loop

OpenDesign's own agent (start_run) is best for rendering-heavy work: it injects DESIGN.md, the skill and craft/ rules, and streams a sandboxed preview. Your harness agent is best for orchestration, cross-checking claims, and moving results into code or channels. The usual split: harness agent writes the brief and reviews; OpenDesign renders.

PART V · 13 · BOSSFANG ORCHESTRATION

Schedules, triggers, workflows and channels — the always-on half of the bench.

BossFang (your LibreFang fork; CLI bossfang, dashboard http://127.0.0.1:4545, config ~/.librefang/config.toml) is the only component here with a real scheduler, an event trigger engine, a DAG workflow engine, human-approval gates, budgets and a tamper-evident audit log. That makes it the conductor. UAR does the thinking where you want UAR's governance and A2UI; BossFang decides when and where the result goes.

Colleague-like, never deceptive

Give agents names and consistent personalities, but disclose that they are AI agents in their profile, their first message in a channel, and anywhere they talk to people outside your bench. Keep them at Level 3 (disclosed representative) or Level 4 (delegated actor under a revocable grant) from the Company-of-One brief. Posting to an external audience, contacting customers, spending money and merging code stay behind approvals — a persona is not a credential.

PART VI · 17 · SETUP CHECKLIST

From zero to a working bench, in order.

  1. Shared services. The Boss → Settings → Prometheus → start managed services (SurrealDB :28000, surreal-memory :23001, liter-llm :4000), or node scripts/services.mjs up in prometheus-skills-mini. Check curl 127.0.0.1:23001/health.
  2. Skills once, everywhere. node scripts/doctor.mjs --fix copy-skills → ~/.agents/skills + ~/.claude/skills; install the Claude and Codex plugin packages; copy into ~/.kimi-code/skills and ~/.minimax/skills. Merge the agent-team-creator branch first.
  3. MCP everywhere. Register surreal-memory (/mcp/http) and open-design (od mcp install <client>) in Claude Code, Claude Desktop, Codex, Kimi Code, MiniMax, The Boss, UAR mcp.json and BossFang [[mcp_servers]].
  4. UAR. Run the service with server-full; mint an API key; set memory to the shared SurrealDB; add deployment Cedar policies and tool-approval rules; register your first agents via compile-and-register.
  5. Brand. In OpenDesign, od brand create https://know-me.tools → finalize → design-systems/knowme/DESIGN.md. Record the brand steward as its only writer.
  6. Teams. For each standing team, run agent-team-creator guide → init → models-select → export; apply the Claude/Codex/Kimi/MiniMax exports to the repo or user scope; register UAR artifacts; choose BossFang agent+workflow or Hand deployment.
  7. BossFang. bossfang init; add [provider_urls]/[a2a] pointing at UAR; add channel sidecars with per-agent accounts; set [budget], [approval], [audit]; create cron jobs and triggers; test each workflow with dry-run.
  8. Switching ritual. Save the switch-in prompt as a skill or slash command in each harness; practise one full Claude Code → Codex → phone handoff before relying on it.
  9. Kill switches. Know how to stop everything: bossfang hand pause, cron disable, stop; UAR run cancel; revoke API keys. Test them.
