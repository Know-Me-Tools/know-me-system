S05-002 · 1. Purpose and scope

Governing revision: UI-01–11 · source requirement, not release evidence.

1. Purpose and scope

This spec defines every Flutter UI/UX surface required by the Unified Inference Recovery and Context Fabric Plan ("the Plan"). It covers what the user sees and touches; it does not restate the Rust contracts except where the UI consumes them. It is written to be implemented delta-first: several surfaces already exist in partial form (§3) and must be formalized, not rebuilt.

In scope:

  • Chat turn anatomy: ordered regions, thinking, lifecycle, tool/skill/memory panels, answer bubble, citations, error/cancelled bubbles.
  • Message actions and branch behavior: Copy, Resubmit, Delete, Regenerate, Stop/Cancel, branch navigation, disabled-state rules.
  • Run lifecycle UI: named phases, model download/load progress, cancellation, accessible announcements, crash-restoration presentation.
  • Composer and attachments: Xberg/OCR states, conversation-scoped documents, promotion to durable knowledge.
  • Models screen: library, download/resume/cancel, verification, backend diagnostics, the OpenCL ≥15% certification gate outcome, active-backend honesty.
  • Context inspector: profile, estimator, slice spending (30/70), dropped items, degradation, escalation advice, unified with the activity/event inspector required by the design standard.
  • Startup and lazy-initialization status surfaces.
  • Settings and configuration schema: context strategy, developer flags, per-assistant fact-extraction opt-in, lane/model selection, cloud presets.
  • Accessibility, motion, golden/behavior test matrices, and acceptance gates.

Out of scope: React/Tauri implementation (the standard governs parity; this spec cites parity expectations where the Flutter surface leads), Rust internals, and any code change authorized by this document alone.

Non-negotiable invariants inherited by every section:

  • Flat 2.0 — no borders, dividers, decorative outlines, or layout shadows; regions differ only by background color (docs/knowme-ui-ux-standard.md §3).
  • Layering — Widget → @riverpod provider → Repository → FFI (Rust core). Widgets are pure projections; state mutates only through providers; the Dart A2UI/FFI mirrors are regenerated, never hand-edited.
  • Tokens — all color/spacing/type/radius values come from the shared token source projected into KnowMeTheme/KnowMePalette (mobile/lib/core/theme/tokens.dart); no raw Color(0xFF…) or magic EdgeInsets at call sites.
  • ContentBlock exhaustiveness — one widget per variant, switch with no default, in gen_ui_widgets (see .kimi-code/skills/content-block-ui).

S05-003 · 2. Governing constraints distilled

Governing revision: UI-01–11 · source requirement, not release evidence.

2. Governing constraints distilled

From the Plan, PAGS-SPEC-KM-CTX-001, the design standard, and project skills — the rules every surface below must satisfy:

  1. Named phases replace spinners. Runs emit RunStatus (queued, preparing, thinking, generating, complete, cancelled, error) and named phases (context assembly, document extraction, OCR, embedding preparation, memory retrieval, knowledge retrieval, tool selection, summarization, model download, verification, loading, fallback selection, tool execution, generation, persistence). The Plan forbids temporary generic spinners at any later stage; the final lifecycle components land with the state machines.
  2. The 11-variant ContentBlock union is closed. Lifecycle and telemetry travel in the run-event envelope, never as new block variants. Unknown provider events surface as ArtifactBlock records (provider, event name, original payload) and are rendered by the artifact widget's raw-event path.
  3. Backend honesty. The active backend (cpu / opencl / metal / cloud), device, offloaded layers, and any fallback reason are visible product information, not debug data. OpenCL is active only when the physical-device certification (correct, thermally safe, ≥15% median improvement) passes; otherwise CPU runs with a visible reason.
  4. Android is text-only and non-thinking. Android attachments always pass Xberg/OCR before the text-only model; no image tensor is submitted and no thinking UI is promised on the Android local lane. The thinking surface is still specified (iOS, cloud, and future models require it) but must degrade to a documented empty state on Android, not a broken one.
  5. Reasoning is displayed, persisted, and quarantined. Thinking blocks render and persist, but prior reasoning is excluded from subsequent prompts, summarization, fact extraction, and tool context. The UI never offers "send thinking back to the model" affordances.
  6. Mutating tools always require confirmation (AlwaysConfirm, non-disableable by non-privileged layers, CTX §7.1/G4). The confirmation surface is a designed, accessible flow — never a raw JSON dump.
  7. Budget UX is a differentiator. The context inspector is a product surface: profile, estimator, slice spending, dropped items, degradation, and escalation advice are all renderable from ContextTelemetryEvent and PromptPlan mirrors (CTX §11.2, §12).
  8. Tightening-only user overrides (CTX §6.6): user-level budget controls may only reduce envelopes, never raise them.
  9. Destruction is confirmed and branch-scoped. Delete removes the response plus its branch tail, invalidates branch summaries, and cleans fact provenance; destructive and resubmit actions are disabled while the affected branch has an active run.
  10. WCAG 2.2 AA everywhere: 4.5:1 body / 3:1 large-text and component contrast in both themes, accessible names on every actionable element, keyboard/focus order, liveRegion announcements for streaming and status, ≥24 px targets (44 px primary touch), reduced-motion path, layouts that survive 200% text scaling.

6. Chat thread — turn anatomy

S05-011 · 6.1 Ordered regions (formalized)

Governing revision: UI-01–11 · source requirement, not release evidence.

6.1 Ordered regions (formalized)

An assistant turn renders, in order:

  1. Thinking region (0..n thinking blocks) — outside the answer bubble.
  2. Lifecycle region — the named-phase strip while the run is active; collapses to a summary line on completion (§6.4).
  3. Activity panels — toolUse/toolResult/skill/memory panels in stream order, outside the answer bubble.
  4. Answer bubble — text/code/artifact/image/divider runs, each maximal contiguous run wrapped in one surface, capped at 80% of viewport width (max 720 px), left-aligned.
  5. Citation attachments — adjacent to the answer content they support (§6.3).
  6. Terminal bubbles — persisted error or cancelled bubble after the last semantic block (§6.5).
  7. Action row — right-aligned, below the turn (§7.1).

The existing _AssistantTurn segmentation implements regions 1–5; this spec formalizes that behavior and adds the lifecycle strip and citation adjacency rules. Region backgrounds come from the surface ladder: panels on surface, the answer bubble on card/raised, thinking on the cyan-tinted surface (§6.2). No region may introduce a border, divider, or shadow.

S05-012 · 6.2 Thinking region

Governing revision: UI-01–11 · source requirement, not release evidence.

6.2 Thinking region

Behavior (formalizing ContentBlockThinking):

  • Expanded while streaming its own block; auto-collapses when answer content begins, unless the user manually expanded or collapsed it. A manual choice always wins over automation for that block.
  • Collapsed header shows: brain/psychology icon, "Thinking" label, and — once terminal — duration metadata ("Thought for 42 s"); while streaming, a live elapsed time replaces any spinner glyph.
  • Body is selectable plain text with whitespace preserved; no Markdown rendering inside thinking; copy button copies the raw trace.
  • Tint: cyan-tinted flat surface per design standard §7.5 (cyan = reasoning/citations/streaming). Current implementation uses the generic secondary surface — migrating to the cyan annotation tint is a formal delta of this spec, applied via tokens in both themes.
  • Android empty state: on the Android local lane (non-thinking Qwen), the region simply never appears. If a thinking toggle exists in settings (§13.3), it is shown disabled with the explanation "The on-device Android model does not produce reasoning traces."
  • Reasoning quarantine is invisible in day-to-day UX except one honesty touch: the inspector's prompt-plan view marks prior thinking blocks as excluded from context (§10.4).
  • Accessibility: header exposes expanded/collapsed state programmatically; body announces via polite live region while streaming; expanded thinking is reachable in keyboard focus order after the header.

S05-013 · 6.3 Citation attachments

Governing revision: UI-01–11 · source requirement, not release evidence.

6.3 Citation attachments

The Plan moves citations from "panel among panels" to adjacent to supported answer content:

  • citation blocks render as compact source chips inline at the end of the answer run they cite (trailing the bubble), not interleaved with tool panels. Each chip: source icon, short label, count badge when several chunks ground the same span.
  • Tapping a chip opens the citation card (existing _BlockSurface pattern): source title, excerpt, provenance (conversation / message / chunk / run), and — for memory citations — a "view memory" jump that opens the Memory destination at that record without losing thread position.
  • Fallback: when a citation arrives before its answer run exists (streaming edge), it renders in the activity-panel region and migrates adjacency on finalization. The block order on record never changes; this is a presentation rule only.
  • Citations use the cyan annotation tint; status is never by color alone (icon + "Citation · {source}" label).

S05-014 · 6.4 Lifecycle region (replaces `_RunStatusBubble`)

Governing revision: UI-01–11 · source requirement, not release evidence.

6.4 Lifecycle region (replaces _RunStatusBubble)

While a run is active, a single strip above the answer area shows the run's named phase — this is the component the Plan requires to exist before any later stage may ship (no generic spinners downstream):

  • Content: phase icon + human phase label ("Retrieving memories", "Reading document", "Selecting tools", "Generating") + elapsed time + Stop affordance (44 px, accessible name "Stop generating").
  • Phase label mapping is a fixed table owned by the presentation layer; an unrecognized phase renders its snake_case name humanized — never a raw enum string, never blank.
  • The strip is a polite live region: it announces on phase change, not on every tick; elapsed time is visual only.
  • On completion the strip collapses to a one-line summary ("Generated in 8.2 s · on-device · CPU") which remains persisted with the message; on error/cancel it is superseded by the terminal bubble.
  • Queued/preparing states before the first phase event show "Preparing response" — this is a named state, not a spinner.
  • Model-bound phases (download, verification, loading, fallback selection) are normally surfaced by the model banner (§8.2); if a run hits them mid-thread (e.g. first send after install), the strip mirrors the same label so the user never sees a dead turn.

S05-015 · 6.5 Error and cancelled bubbles (extended)

Governing revision: UI-01–11 · source requirement, not release evidence.

6.5 Error and cancelled bubbles (extended)

Existing _RunErrorBubble / _RunCancelledBubble are extended, not replaced:

  • Error bubble content, in order: error icon, safe message (plain language, from RunError.message — never a transport exception string), phase chip (e.g. "while loading model"), stable code in mono metadata, and a retry affordance when retryable ("Try again" re-runs the originating user message through the same path as Regenerate).
  • Non-retryable errors state the recovery path in one sentence ("This model file failed verification. Re-download it from the Models screen.") with a deep-link action where one exists.
  • Cancelled bubble: stop icon + "Response cancelled" + elapsed-before-cancel; no destructive styling (secondary surface).
  • Crash-restoration variant: when a restored message has a non-terminal run status that can never resume (process death), the terminal bubble reads "Interrupted when the app closed" with a "Regenerate" action. Restoration must reproduce exact block order, status, and diagnostics; partial blocks keep their content with a "restored partial response" metadata line.
  • Both bubbles persist with the message and appear in goldens (§15).

S05-016 · 6.6 Tool, skill, and memory panels (formalized)

Governing revision: UI-01–11 · source requirement, not release evidence.

6.6 Tool, skill, and memory panels (formalized)

  • Panels render status, not raw JSON: pending → running → complete/failed with disclosure for input/output (existing _DisclosureBlock pattern).
  • AlwaysConfirm flow: a mutating tool renders the confirmation card in the panel region: tool name, human description of the mutation, parameters summary, consequence text, and Confirm / Deny actions (44 px, safe default = Deny, keyboard-focusable, announced as an alert). Confirmation resumes the exact stored call (existing local_tool_approve interaction); denial records a failed/skip result so the model can continue.
  • Restored confirmations that can no longer resume (process-local approvals) show the existing "resubmit to create a fresh approval request" guidance — keep this copy.
  • Repair attempts are visible: "Retrying tool call (2 of 2)" as panel status metadata, from the bounded-repair contract.
  • Skill panels show skill identity + status + output summary behind disclosure; memory panels distinguish recalled / proposed / written / updated / rejected (existing mapping) and link to the Memory destination.

S05-017 · 6.7 Backend chip

Governing revision: UI-01–11 · source requirement, not release evidence.

6.7 Backend chip

Every assistant turn carries a small metadata chip (mono, faint text, non-interactive-by-default): model short name + backend + lane, e.g. Qwen3-4B · CPU · on-device or Qwen3.5-9B · Metal · on-device or Gemma-4 · Cloud. When fallbackReason exists, the chip gains a warning icon and opens the inspector's diagnostics section on tap (e.g. "CPU selected: OpenCL requires a physical-device certification…"). Lane wording follows the standard's "On-device / My server / Cloud provider" trichotomy.

7. Message actions and branch behavior

S05-019 · 7.1 Action inventory and rules

Governing revision: UI-01–11 · source requirement, not release evidence.

7.1 Action inventory and rules

Action On Behavior Disabled when
Copy block Every block header (exists) Copies that block's canonical text Never
Copy answer Assistant action row (exists) Copies answer-region blocks only (not thinking/panels) Empty answer
Copy message User bubble (exists) Copies full user content Never
Stop/Cancel Active run (send button morphs, exists; lifecycle strip, §6.4) Emits cancellation; terminal cancelled bubble follows Not disabled while active
Resubmit User message Creates a new branch: saved user content + attachments + branch prefix + current settings + newly assembled context plan Affected branch has an active run

  • Delete confirmation copy states the blast radius: "Delete this response and the N messages after it on this branch? Memories saved from them are removed too." Confirm is destructive-styled; recovery is not promised.
  • All actions keep ≥48 px hit constraints (existing), tooltips, and accessible names; the action row is reachable after the turn content in focus order.

S05-020 · 7.2 Branch navigation (new)

Governing revision: UI-01–11 · source requirement, not release evidence.

7.2 Branch navigation (new)

Branches are invisible today; the Plan makes them first-class:

  • Any message with siblings (created by Resubmit/Regenerate) shows a compact branch navigator trailing the turn: ‹ 2/3 › monochrome, 44 px targets, accessible label "Response 2 of 3, branch {branchId}".
  • Switching swaps the branch tail in place with the persisted block order of the selected sibling; scroll anchor stays on the navigator's message.
  • The active branch id is conversation state, restored on relaunch; the conversation header shows a "Branch" badge when viewing a non-main branch, with a "Jump to main" action.
  • The conversation library marks branched conversations (existing branched view expectation in the standard §7.8).
  • Branch creation is never silent: a one-line divider-less metadata row in the thread marks "Branched from an earlier message" at the fork point.

8. Models surfaces

S05-022 · 8.1 Models screen (new — `features/models`)

Governing revision: UI-01–11 · source requirement, not release evidence.

8.1 Models screen (new — features/models)

Design standard §9: "a user-owned library, not a storefront." Sections:

  1. Active model card — model name, quant (Q5_K_M), size on disk, lane ("On-device"), acceleration backend (CPU / OpenCL (Adreno) / Metal), device name, offloaded layers when known, and status (Ready, Not installed, operation-in-progress). Android copy names the model honestly: "Qwen3-4B-Instruct-2507, Q5_K_M, ~2.9 GB".
  2. Backend row — active backend with certification summary: "OpenCL locked: needs an on-device benchmark ≥15% faster than CPU" or "OpenCL certified: +23% median, thermally safe" or "CPU active: certification failed (correctness)". A "Re-run benchmark" action lives here (developer section mirrors it), producing the certification artifact the Rust gate consumes. Benchmark UX shows: running state with per-config progress (CPU run, OpenCL run), thermal readings, and the pass/fail verdict with the three criteria itemized.
  3. Available models — the pinned catalog (Android: Qwen3-4B; iOS: Qwen3.5 9B) with capability tags (text-only / vision / reasoning), context figures (§8.4), and per-model state + primary action (Download / Resume / Cancel / Delete / Activate).
  4. Remote models — BossFang-linked remote entries marked "Remote — runs on your server", visually and verbally distinct from local (standard §7.3 trichotomy); no remote row may look installed when it is not.
  5. Cloud presets — baked, versioned presets listed read-only with provider, model, and capability tags; enabling one requires the lane/BYOK configuration in Settings (§13.2) and is marked "Cloud".

Empty state (no model installed): explains local-first value, download size and time expectation, and one primary "Download Qwen3-4B" action — matching the standard's "one-action recovery" rule.

S05-023 · 8.2 Model operation banner (extended)

Governing revision: UI-01–11 · source requirement, not release evidence.

8.2 Model operation banner (extended)

The existing chat _ModelOperationBanner extends to the full ModelOperationState machine:

  • States and copy: Not installed → slim info bar "No local model yet — chat uses cloud until one is installed" + action; Downloading → percent, data rate, resumable indicator ("resumes after interruption"), Cancel; Verifying → indeterminate-with-label; Loading → "Loading model into memory"; Ready → auto-dismiss with a transient confirmation; Cancelling → label only; Cancelled → "Download cancelled — resume anytime" + Resume; Failed → RunError safe message + retry/deep-link.
  • The banner is the single place model operations appear in chat; the Models screen shows the same state machine on the active-model card (one source of truth via the shared provider).
  • Polite live region announcing state transitions only; progress percent is visual.

S05-024 · 8.3 Download integrity presentation

Governing revision: UI-01–11 · source requirement, not release evidence.

8.3 Download integrity presentation

  • Verification state is named ("Verifying download"), never folded into the progress bar.
  • A failed checksum deletes the artifact and shows "Download failed integrity check and was removed" with a retry — this is the honesty standard applied to model files.
  • Byte counts use the pinned catalog values; resumed downloads show "resumed at N%" once.

S05-025 · 8.4 Capability honesty (nominal vs trusted context)

Governing revision: UI-01–11 · source requirement, not release evidence.

8.4 Capability honesty (nominal vs trusted context)

Model rows and the inspector show two figures with an explainer (CTX §6.2): nominal context ("256K tokens — the model's advertised window") and trusted ceiling ("8K tokens — verified reliable on this device"). The explainer sheet (one tap on the figures) states: ceilings come from on-device measurements, 16K is available in Developer settings, and raising the ceiling trades reliability for history. iOS rows show the same pattern with the 9B profile.

9. Composer and attachments

S05-027 · 9.1 Attachment strip (extended)

Governing revision: UI-01–11 · source requirement, not release evidence.

9.1 Attachment strip (extended)

Existing chip strip (25 MiB / 6-file guards, error line) gains per-chip extraction state once sent is pressed and extraction begins:

  • pending → extracting → OCR → ready → failed, shown as a state dot + label on the chip ("Reading", "OCR", "Ready", "Couldn't read").
  • Android rule surfaced honestly: images and scans show "Text will be extracted — the on-device model can't see images directly" as a one-time hint under the strip (dismissible, per-conversation memory).
  • Extraction failure never blocks silently: the chip turns destructive-tinted with the safe message, and send proceeds only after the user removes the failed file or explicitly sends without it (a per-chip "Send anyway as file reference" is not offered on Android's text-only lane; cloud lane keeps original parts per the Xberg pipeline doc).
  • Limits remain: 25 MiB/file, 6 attachments, 512 KiB extracted text into context; hitting the text cap shows "Only the first part of this document fits the context" on the chip.

S05-028 · 9.2 Attachment blocks in the thread

Governing revision: UI-01–11 · source requirement, not release evidence.

9.2 Attachment blocks in the thread

Sent attachments render as artifact blocks (existing ContentBlockDocumentPreview path) with extraction metadata on disclosure: extracted length, OCR used (yes/no), and warning when extraction partially failed. The block header action copies the extracted text.

S05-029 · 9.3 Conversation documents panel (new)

Governing revision: UI-01–11 · source requirement, not release evidence.

9.3 Conversation documents panel (new)

Plan §5: uploaded documents are conversation-scoped by default. A header-level "Documents" sheet per conversation lists:

  • Each ingested document: name, mime, size, chunk count, extraction state, and ingestion time.
  • Scope marker: "Stored with this conversation — deleted when it is deleted."
  • Promote to Knowledge action per document: moves chunks to durable knowledge with provenance intact; confirmation explains the scope change ("Available to all future conversations; governed by Memory settings").
  • Delete action per document (removes its chunks from this conversation's retrieval, with confirmation).
  • Empty state: "Files you send in this conversation can be searched in follow-up questions."

S05-030 · 9.4 Retrieval visibility

S05-039 · 12. Startup and lazy initialization (extended)

Governing revision: UI-01–11 · source requirement, not release evidence.

12. Startup and lazy initialization (extended)

The Plan decouples startup: only FFI, the entity database, the SurrealDB schema, and compatibility metadata open eagerly; FastEmbed, seeds, Xberg/OCR, downloads, and inference initialize lazily with named status.

  • StartupGate keeps its current eager phase progress (migrations, schema) but the eager path must reach the usable shell within the 5-second cold- start gate; everything lazy moves out of the blocking sequence.
  • A lazy-init status surface replaces blocking spinners for deferred subsystems: a subtle header chip (or Home instrument row) listing deferred components with named states — "Document reader: starting" / "Embeddings: ready" / "Model: not installed". Each resolves independently; failures surface per-component with a retry, never as an app-level boot error.
  • Feature-level gating: invoking a feature whose dependency is still lazy (e.g. sending an attachment before Xberg is ready) shows the named preparation state inline ("Preparing document reader…") and completes without user intervention; it never dead-ends.
  • Boot errors remain blocking and visible only for the eager set (migrations/schema/FFI), per the existing _BootError.

S05-048 · 14. Accessibility and motion requirements (per surface)

Governing revision: UI-01–11 · source requirement, not release evidence.

14. Accessibility and motion requirements (per surface)

Global floor: WCAG 2.2 AA as itemized in §2.10. Per-surface specifics:

  • Streaming text/thinking: polite liveRegion semantics; no per-token announcements — announce phase changes and completion, not deltas.
  • Thinking/panels: expanded state programmatic (Semantics(expanded:)); disclosure controls labeled; focus order: panels → answer → actions.
  • Lifecycle strip: phase transitions announced; Stop reachable by keyboard at all times during a run; Escape cancels when focus is in the thread.
  • Confirmations (tool/delete/promote): alert semantics, safe default focused first, destructive action last in order, Escape = safe choice.
  • Branch navigator: Semantics(button, label: 'Response 2 of 3'); switch announced.
  • Charts/meters in the inspector: meter fills are decorative; values always paired with text (never color-only), slices readable top-to-bottom by screen reader.
  • Targets: 44×44 for all touch actions (existing 48 px constraints meet this); inspector chips ≥44 px.
  • Text scaling: all layouts verified at 130% and 200% scaler without overflow; bubbles use max-width + flexible wrapping; the inspector tables collapse to stacked rows at ≥130%.
  • Reduced motion: auto-scroll becomes instant (exists); strip transitions, panel expansions, and sheet presentations become opacity-only or instant; no parallax or physics animations anywhere in these surfaces.
  • Themes: every surface specified here renders in both palettes from KnowMeTheme; cyan/ember/status tints verified against resolved foreground pairs, not token names.
