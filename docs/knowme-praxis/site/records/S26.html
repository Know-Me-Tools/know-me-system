S26-001 · Local Model Acquisition & Management Strategy

Governing revision: CX-01–08 · source requirement, not release evidence.

Local Model Acquisition & Management Strategy

Scope: how KnowMe selects, downloads, verifies, and activates on-device models across web, desktop (macOS/Windows/Linux), and mobile (iOS/Android) — including first-run onboarding, per-environment hardware detection, distribution (Hugging Face vs. a KnowMe-controlled origin), and post-download validation.

Status: v1.2 strategy, 2026-07-18 (v1.1 added §10 per-machine picks and §11 embeddings; v1.2 adds §12 Model Library UX). Companion to docs/knowme-functional-spec.html (§04 Models tile, §10 Tiers) and docs/knowme-builder-extensibility-spec.md (§7 packaging). Implements against rust/crates/gen_ui_inference (llama-cpp-2 + reqwest/sha2, mistral.rs optional) and the versions.toml [inference] matrix (desktop/mobile = llama-cpp-2, web = WebLLM).

S26-002 · 1. Principles

Governing revision: CX-01–08 · source requirement, not release evidence.

1. Principles

  1. The catalog is signed data, not code (§4). Models, quants, sizes, hashes, licenses, and hardware requirements ship as a versioned manifest the app fetches and verifies — never as constants in the binary.
  2. Recommend, never force. Detection produces a recommendation with a visible reason ("8 GB unified memory → Gemma-3n-2B-Q4"); the library stays open (sideload, override). This is the "library, not a menu" stance from the moodboard.
  3. The first token is the onboarding goal. Everything in §2 is ordered so the user reaches a working first generation as fast as their connection allows, with honest progress and a working app while they wait.
  4. Trust is structural: SHA-256 on every artifact, signed manifests, and a load-and-generate smoke test before a model is marked Active (§7). llama.cpp does not verify integrity at load time — there is an open upstream request for exactly this (ggml-org/llama.cpp#15250) — so verification is our job, in the acquisition layer.
  5. One state machine, three transports. Discovery → fit-check → consent → fetch → verify → activate is identical everywhere; only the fetch adapter differs per tier.

S26-003 · 2. Onboarding (first run)

Governing revision: CX-01–08 · source requirement, not release evidence.

2. Onboarding (first run)

The Engine Card is the destination: green dot, model name, live tok/s. First run is the path to lighting it up.

Step 0 — instant utility. The app must be usable before any model lands: UI opens, settings work, and (web/desktop) a "connect to a BossFang instance or cloud provider" escape hatch exists so a user on hotel Wi-Fi isn't staring at a progress bar. If a peer instance is reachable, offer remote inference now while the local model downloads in the background.

Step 1 — probe (silent, <1 s). Run the DeviceProfile probe (§3). No consent needed; nothing leaves the device. Cache in settings; re-probe on hardware change (eGPU, RAM upgrade, browser update enabling WebGPU).

Step 2 — recommend (one card, one number). Show a single recommended model with size, why it was chosen, and what it costs: "Gemma-3n-2B-Q4 · 1.5 GB download · runs ~47 tok/s on this Mac." Secondary link: "choose a different model" opens the full library with fits / tight / won't-fit badges. License display happens here (§5.4): permissive licenses (Apache-2.0/MIT) get a link; restricted-license models get an explicit acceptance step before download.

Step 3 — consent to the download, with the right defaults per tier. - Desktop: start immediately on click; show resumable progress in the Engine Card slot. - Mobile: disclose size prominently; default Wi-Fi only (user can override to cellular); warn on low storage or low battery; the download survives app suspension (§6.3). - Web: check navigator.storage.estimate() against the artifact size first; request navigator.storage.persist(); if the browser lacks WebGPU or refuses persistence, say so plainly and offer the smaller/CPU-lane model or a remote instance instead.

Step 4 — verify + activate (§7), then benchmark. The first activation runs the 30-second micro-benchmark; its measured tok/s becomes the Engine Card number and is stored in the device profile. If decode lands under the usability floor (~8–10 tok/s), offer the next model down with the measurement as the reason.

Step 5 — background upsell, never a blocker. Larger models the hardware can carry ("this machine could run Gemma-4-3B — 2.1 GB") appear as a dismissible suggestion in the Models tile, never as onboarding friction.

Re-onboarding paths reuse the same flow: new device via OFP (peer already has the GGUF → LAN fetch, §5.3), restored backup (models are excluded from backups → re-offer), storage eviction (web/mobile → detect at load, §7, re-offer).

S26-006 · 3.2 The fit test

Governing revision: CX-01–08 · source requirement, not release evidence.

3.2 The fit test

fits :=  weights(quant)
       + kv_cache(ctx_len, n_layers, kv_quant)
       + compute_buffers
       + headroom            <  budget
  • budget = VRAM on discrete GPUs; 60–70 % of unified/system RAM elsewhere (the app, SurrealDB, and the OS live in the same pool — on iOS use the jetsam-derived figure).
  • Choose quant by budget: Q4_K_M default; Q8_0 when abundant; when constrained, drop a model size tier before dropping below Q4 — harsh quants degrade quality faster than smaller models do.
  • Context length is part of the equation: the same model "fits" at 4k and doesn't at 32k. The recommendation pins a default ctx per device tier and says so.

S26-007 · 3.3 Heuristics propose, benchmarks decide

Governing revision: CX-01–08 · source requirement, not release evidence.

3.3 Heuristics propose, benchmarks decide

Static detection selects the candidate; the first-activation micro-benchmark (short prefill + ~64-token decode, measured separately) is the source of truth for the Engine Card and for downgrade/upgrade suggestions. Store {model, quant, backend, prefill_tps, decode_tps, measured_at} in the device profile. Never show a user a guessed tok/s when a measured one exists.

5. Distribution: Hugging Face vs. a KnowMe-controlled origin

S26-010 · 5.1 The decision

Governing revision: CX-01–08 · source requirement, not release evidence.

5.1 The decision

Primary: a KnowMe-controlled origin. Hugging Face as fallback. HF tokens only for genuinely gated models the user brings their own account for.

The licensing landscape makes this clean for the entire curated catalog: Qwen and Mistral ship Apache-2.0, Phi ships MIT, and Gemma 4 moved to Apache-2.0 in 2026 (VentureBeat, MindStudio); earlier Gemma generations use the Gemma Terms of Use, which permit redistribution with pass-through of the use restrictions — which is exactly how Ollama serves Gemma from its own registry today (ollama.com license blob). So we can legally mirror everything in the default catalog and control our own availability, latency, and versioning.

Why not HF as primary: HF's gated-model access is granted to individual users, never to organizations — a shared org token cannot download gated repos on users' behalf (HF gated-models docs) — and resolve-URL semantics, rate limits, and repo layout changes are all outside our control. HF remains a listed fallback source for permissive models (anonymous resolve/main/<file> URLs work ungated — HF downloading docs) and the only path for gated models, where the flow is: user pastes their own HF token (stored in OS keychain via Tauri secure storage; per-user, per HF policy — HF token docs).

S26-011 · 5.2 The KnowMe origin, concretely

Governing revision: CX-01–08 · source requirement, not release evidence.

5.2 The KnowMe origin, concretely

  • Storage/CDN: Cloudflare R2 behind a custom domain (models.know-me.tools) — zero egress fees make multi-GB artifacts economically sane (R2 overview), and a custom-domain public bucket with CDN caching is the recommended pattern for large public artifacts (R2 access patterns, community guidance).
  • Auth model: no authentication for free-catalog artifacts. Integrity comes from the signed manifest + SHA-256, not from access control; anonymous download is a feature (no account required — FUNC-SPEC §09 "no central account"). Range requests work natively, which resumable downloads (§6) depend on.
  • Pro-tier licensed models (the Qwen-35B-class artifacts) are the one place owned auth earns its keep: a license key (issued at purchase, stored in keychain) is exchanged at a tiny token service for a short-lived presigned URL (R2 presigned URLs) or passed to a Cloudflare Worker gate in front of the private bucket (Worker-gated R2 pattern). Keys authorize download, not inference — once fetched and verified, the model runs offline forever, preserving the sovereignty guarantee.
  • Layout: content-addressed, Ollama-style. Store blobs under /blobs/sha256/<digest> with catalog manifests pointing at digests — the OCI-like blob/manifest split Ollama uses is the proven shape for model distribution (Ollama storage internals, DeepWiki: registry & layers). This makes the same blobs trivially publishable to IPFS (same digests → CIDs) and to an OCI registry later, aligning with the .pxt distribution story in the extensibility spec.

S26-012 · 5.3 Source preference order (per artifact, walked by the fetcher)

Governing revision: CX-01–08 · source requirement, not release evidence.

5.3 Source preference order (per artifact, walked by the fetcher)

  1. LAN/OFP peer that already holds the digest (BossFang instance) — free, fast, sovereign;
  2. KnowMe origin (R2/CDN);
  3. IPFS gateway (own gateway first, public fallback) — same digest;
  4. Hugging Face resolve URL (anonymous, or user token if gated).

Every source yields bytes that must hash to the same SHA-256; a source that fails verification is skipped and reported, never trusted.

S26-015 · 6.1 Shared semantics (all tiers)

6.1 Shared semantics (all tiers)

Persistent DownloadTask records in SurrealDB: {model, artifact, source, bytes_total, bytes_done, state} with states queued → fetching → verifying → smoke-testing → ready | failed(reason). Preflight checks disk space (artifact + 10 % slack). Fetch to <digest>.part, atomic rename into the content-addressed store on verification. S26-016 · 6.2 Desktop (Tauri) — the reference implementation

Governing revision: CX-01–08 · source requirement, not release evidence.

6.2 Desktop (Tauri) — the reference implementation

Rust in gen_ui_inference (reqwest is already wired): HTTP Range resumption, 3–4 parallel range segments for large files, streaming SHA-256 (sha2 already a dep), bandwidth cap setting, retry with exponential backoff + resume from bytes_done. Store under <app-data>/models/blobs/sha256/<digest>; a models/registry.json maps human names → digests (mirroring §5.2's layout locally, which is what makes peer-serving trivial for BossFang).

S26-017 · 6.3 Mobile — use the OS transfer service, not reqwest

Governing revision: CX-01–08 · source requirement, not release evidence.

6.3 Mobile — use the OS transfer service, not reqwest

A foreground Rust download dies on suspension. Use URLSession background sessions on iOS (survives suspension and app termination; OS-managed retry; delegate wakes the app on completion — mind the gotchas: background sessions are discretionary under Low Power Mode/poor connectivity, per Apple's forums guidance and field notes) and WorkManager-scheduled DownloadManager on Android (constraint-aware: unmetered network, storage, battery). The FRB bridge only observes: platform code reports progress/completion; Rust verifies the hash and finalizes. Defaults: Wi-Fi-only (overridable), no auto-start on cellular, isExcludedFromBackup = true on iOS (models must not inflate iCloud backups), never bundle weights in the app binary.

S26-018 · 6.4 Web — delegate to WebLLM, manage the edges

Governing revision: CX-01–08 · source requirement, not release evidence.

6.4 Web — delegate to WebLLM, manage the edges

WebLLM fetches shards and caches via the Cache API (or IndexedDB via appConfig.cacheBackend) (docs). KnowMe's appConfig points model URLs at the KnowMe origin (§5.2) rather than HF. Around it: storage.estimate() preflight; storage.persist() request with honest messaging when denied; eviction detection at engine init (cache miss → re-offer); WebGPU absence → offer the wllama/WASM-CPU lane for small models or a remote instance (the dual-lane pattern in webgpu-webllm-app). Safari today means "small models or remote" — say it, don't fake it.

S26-019 · 7. Post-download validation

Governing revision: CX-01–08 · source requirement, not release evidence.

7. Post-download validation

Marking a model Ready requires all five gates, in order:

  1. Hash gate — streaming SHA-256 equals the manifest digest (web: per-shard).
  2. Format gate — parse the GGUF header/metadata (magic, version, tensor count, arch) without full load; catches truncation and wrong-file errors cheaply. GGUF corruption and version drift are the top field failure classes (corruption guide, load-failure taxonomy).
  3. Load gate — actually instantiate on the selected backend with the profile's ctx/offload settings; catches OOM-at-load, backend/driver issues, unsupported quant-arch combos. On failure, retry once on the CPU lane to distinguish "bad file" from "bad backend" and report accordingly.
  4. Smoke gate — one short deterministic generation (fixed prompt, temp 0, ~16 tokens): asserts non-empty, valid UTF-8, no NaN/garbage repetition. Not a quality eval — a "the tensors are sane" check. (This is the layer llama.cpp itself doesn't provide — #15250.)
  5. Benchmark gate (first activation) — the §3.3 micro-benchmark; records measured tok/s; triggers the downgrade suggestion below the usability floor.

Re-validation: gates 1–2 re-run whenever the file's mtime/size changed or after storage eviction events; a Ready model that fails gate 3 at any later launch is demoted to needs-repair with a one-click re-download (blobs are content-addressed, so repair means "fetch the digest again", not "figure out what broke").

S26-023 · 11. Embedding models for RAG (all tiers)

Governing revision: CX-01–08 · source requirement, not release evidence.

11. Embedding models for RAG (all tiers)

The memory/RAG layer (SurrealDB graph + sqlite-vec on mobile, PGlite/pgvector on web/desktop, Postgres+pgvector on flint-forge) needs embeddings everywhere the LLM runs — and unlike chat models, the embedding model must be consistent per index: vectors from different models (or different truncation dims) don't compare. The catalog therefore stamps {embedding_model_id, dim} into every index/KB it creates, and OFP sync treats a mismatch as a re-embed job, not a merge.

Truncate to 256 on mobile (sqlite-vec size/speed), keep 768 on desktop/server — same model, so re-embedding on upgrade is optional, but dims must match within one index

Tiering that falls out: phones and web embed with EmbeddingGemma@256 locally (queries always embeddable offline); desktop embeds with Qwen3-Embedding-0.6B@768 or EmbeddingGemma@768; BossFang/flint-forge can maintain a BGE-M3 hybrid index for the heavy corpus and serve it to devices via the read path — devices keep a local EmbeddingGemma index over their own hot subset. Embedding artifacts flow through the same §5 origin, §6 downloader, and §7 gates (smoke test: embed a fixed sentence, assert dim + finite norm + cosine-similarity sanity against a stored reference vector). Sources: BentoML open-source embedding guide, Milvus 2026 comparison, Ollama embedding benchmark.

S26-024 · 12. The Model Library UX — choose anything, recommend the best

Governing revision: CX-01–08 · source requirement, not release evidence.

12. The Model Library UX — choose anything, recommend the best

The §10 picks are defaults, not walls. The product stance (moodboard Screen 08: "a library, not an offering") is that the user may run any model they can name — curated, community, or sideloaded — and the UI's job is to make the consequences legible before the download, not to gatekeep. This section specifies that surface.

S26-025 · 12.1 Two shelves, one treatment

Governing revision: CX-01–08 · source requirement, not release evidence.

12.1 Two shelves, one treatment

  • Curated shelf — the signed KnowMe catalog (§4/§5): the small artifact set from §10, each entry carrying verified hashes, license metadata, and requirement blocks. Trust pill: green curated (same visual grammar as the plugin installer's Ed25519 verified pill — one trust language across the app).
  • Open shelf — live search of the Hugging Face GGUF universe (LM Studio's Discover pattern: query HF directly, list every quant "sized for your machine" — LM Studio guide). We read the GGUF metadata HF exposes per file (arch, params, quant) remotely, so the fit-check (§3.2) runs before any bytes move. Trust pill: amber community (unverified hash source; we compute and pin the SHA-256 ourselves on first fetch), plus the gated-model token flow from §5.1 when applicable.
  • Sideload — drop a .gguf anywhere (drag onto the Models tile, or the watched models folder): registered through the same gates (§7), badge sideloaded, no network at all. This is the sovereignty proof point and it must never feel second-class.

Every shelf renders the same model-row component from the moodboard (status dot · name · size · backend/speed pill · action), extended with two new pill classes: fit and trust. No separate "advanced" browser — one library, filterable.

S26-026 · 12.2 Fit badges — the traffic light, with reasons

Governing revision: RT-01–11 · source requirement, not release evidence.

12.2 Fit badges — the traffic light, with reasons

Computed per artifact × this device's DeviceProfile, in the moodboard's existing color vocabulary (green/amber/red pills, ember for active):

Badge Meaning Row behavior
recommended (ember) Top pick for a declared use (§12.3) on this hardware Sorted first; reason string shown inline
fits (green) Passes §3.2 with headroom One-click download
tight (amber) Fits only with reduced ctx / partial offload / swap risk (LM Studio's yellow-badge case: "spills to swap, which murders throughput") Download allowed; the mitigation is stated: "runs at ctx 4k" / "CPU-offloads 12 layers, est. ~9 t/s"
won't fit (red) Fails even minimal config Not hidden, not disabled: explicit override with a double-confirm ("needs ~21 GB; this device budgets 10.5 GB — it will not load") — the user owns the machine

Numbers beat adjectives everywhere: each badge expands (tap/hover) to the actual arithmetic — weights + KV(ctx) + buffers vs. budget — in the cyan annotation style the moodboard uses for design-intent callouts.

S26-027 · 12.3 Recommendation chips — per use, with visible reasons

Governing revision: CX-01–08 · source requirement, not release evidence.

12.3 Recommendation chips — per use, with visible reasons

Recommendations are per task, not global — small chips on the library header filter and re-rank: Daily driver · Agents/Hands · Vision · Coding · Embeddings. Selecting "Agents/Hands" surfaces the §10 tool-calling floor as UX: models under the reliability floor for this device get a one-line caution ("under ~7B, multi-step tool calls become unreliable — fine for chat and drafting"), and the recommended agent-tier model for this hardware wears the ember pill. Every recommended pill carries its reason string ("best quality within your 16 GB unified-memory budget at ≥30 t/s") — the recommendation is an argument, never an oracle.

S26-028 · 12.4 Estimated vs. measured performance

Governing revision: CX-01–08 · source requirement, not release evidence.

12.4 Estimated vs. measured performance

For any model we haven't run here — including every open-shelf model — show estimated decode speed with an explicit tilde ("est. ~25 t/s"), derived from the device's measured memory bandwidth (calibrated once by the §7 benchmark gate on a known model; decode is bandwidth-bound, so est ≈ bandwidth / bytes-per-token(active params × quant)). After first activation, the measured number replaces the estimate everywhere (Engine Card, model row, recommendation reasons) and the row is marked measured. Never display a guess in the same typography as a measurement.

S26-029 · 12.5 Per-model configuration, defaults from the profile

Governing revision: CX-01–08 · source requirement, not release evidence.

12.5 Per-model configuration, defaults from the profile

Each model row opens a detail sheet (engine-card layout: stats grid, license, source, hash, run history): ctx length, GPU offload, KV quant, threads — all defaulted by the fit-checker, all overridable, with the fit badge recomputed live as the user drags ctx up ("32k ctx moves this model to tight"). Overrides persist per model per device (device-scoped settings, per the extensibility spec's settings model). Where an MLX or alternative-format build exists for the platform (Apple Silicon), prefer it in the default artifact choice and say why — mirroring LM Studio's format preference cue.

S26-030 · 12.6 What we deliberately do differently from the other tools

Governing revision: CX-01–08 · source requirement, not release evidence.

12.6 What we deliberately do differently from the other tools

LM Studio's compatibility badges and HF-direct search are the right patterns and we adopt them; Ollama's one-command simplicity maps to our curated one-click defaults. Where we diverge: (1) reasons everywhere — no unexplained "should work"; every badge expands to arithmetic, every recommendation to an argument; (2) one trust grammar — model pills and plugin pills use the same verified/community/unsigned visual language; (3) remote models in the same library — BossFang-hosted models sit in the same list with the cyan remote pill (moodboard Screen 08), so "choose any model" includes models your other machines can serve; recommendations may legitimately conclude "run this one on your Mac Pro instead" — that's a recommendation, not a failure; (4) task-scoped recommendation chips rather than a single global ranking.
