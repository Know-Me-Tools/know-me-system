Multi-Agent Development, KBD Process Loops, and Specialist Roles 
 A revised, skill-aware edition covering durable coordination, specialist agents, customer-feedback loops, and heterogeneous execution harnesses.

This edition preserves the original five-part structure and its central ideas: scoped workers, independent evaluation, durable process state, bounded loops, and cross-harness handoffs. Addenda A–D introduce specialist roles, a customer-feedback and enhancement-intake loop, a researched skill catalog, and portable role templates. 
It also corrects several assumptions in the original. Current installed KBD uses an event journal as authority and compatibility JSON as projections ( KBD contract ). Codex supports native agent roles; Part IV gives the sourced harness comparison ( Codex source ). Worktrees isolate edits but do not enforce a security sandbox, and recovery must reconcile in-flight actions rather than promise zero loss ( handoff contract ). 
 Status. This is a design and operating-model document. Role definitions, routing policies and templates are recommendations unless explicitly described as verified current behavior. Reading it does not install skills, create agents, authorize customer communication, or create issues.

 PART I 
Multi-agent theory 
 1.1 Why use several agents? 
Separate agents are useful when they create a meaningful boundary: 
 Boundary Benefit Remaining limitation 
 Context Each worker receives a bounded problem and relevant evidence A bad task brief can still omit essential constraints 
 Responsibility Designer, implementer, tester and evaluator produce different outputs Different titles do not guarantee independent judgment 
 Authority Each role receives only the tools and resources its assignment requires A prompt or skill file alone does not enforce permissions 
 Lifetime A worker can finish while the project continues Recovery still needs durable records and reconciliation 
 Parallelism Independent tasks can proceed together Shared files, state and external actions need coordination 
Use a single agent for a small, coherent task. Add agents when isolation, specialization, independent evaluation or useful parallel work justifies the dispatch and coordination cost. 
 A role is an accountability boundary, not necessarily a permanently running process. One developer may use several roles sequentially. Several developers may share a pool of the same role definitions, with distinct project, tenant and task scopes. 
 1.2 Three coordination models 
 Model Mechanism Appropriate use 
 Orchestrator and workers A coordinator assigns bounded work and collects results Work decomposition and independent parallel tasks 
 Pipeline A stage consumes the preceding stage’s accepted artifact Assess, analyze, specify, plan, execute and evaluate 
 Shared durable state Participants read a common authority and submit controlled changes Recovery, auditability and cross-harness operation 
KBD combines these models. A stage pipeline defines the lifecycle, an authoritative runtime records transitions, and orchestrators dispatch workers within stages. Conversations and agent-to-agent messages can transport information, but they do not replace the durable record of accepted work. 
 Fig. 1 · Pipeline over a journal-backed authority Expand 
 FIG. 1 The pipeline defines the lifecycle; the append-only journal is the authority. Workers read generated views, confirm the runtime revision, and return reports — a single control-plane writer turns accepted results into typed commands. *Copilot is added in this edition and is outside the researched source set. 
 Deployment boundary. A filesystem-backed journal works for its documented deployment boundary. Different machines do not share authority merely because they have clones of the same repository. 
 1.3 The determinism boundary 
 Agents 
Analyze requirements, design, implement, diagnose and review. The model may propose “this change is complete.” 
 Deterministic host logic 
Validates task identity, authority, revisions, transition preconditions and recorded completion — checking whether the proposed transition is valid for the assigned change and current revision. 
Passing a syntactic transition check does not prove the design is correct; independent evidence and evaluation remain necessary. 
Prefer replaceable workers with durable inputs, outputs and checkpoints. A crash can still leave an uncommitted edit, a running tool or an external API action whose outcome is uncertain. Recovery must reconcile those cases before replaying work. 
 1.4 Maker and evaluator are separate assignments 
An implementer can run tests and self-check. A separate evaluator judges the resulting artifact against the specification and evidence. Fresh context reduces dependence on the implementer’s narrative. A different model can add diversity, but neither measure guarantees correctness. A different harness is not necessarily a different model or provider. 
The evaluator receives the goal, constraints, exact artifact revision, relevant source and evidence. It produces findings or a verdict, not a hidden repair. A repair becomes a separately scoped executor assignment, followed by review of the new revision. For code, design, documentation and security alike, distinguish four things:

 1.5 Loops need stopping conditions and budgets 
Give every loop an acceptance condition, attempt/time/cost limits, blocker behavior and a pause path. Completion of a roadmap does not authorize endless background work.

 PART II 
KBD as the coordination substrate 
 2.1 Current authority: journal, projections and artifacts 
For the installed runtime-managed KBD contract, the append-only journal at .kbd-orchestrator/runtime/events.jsonl is authoritative. Waypoint, progress and position JSON are generated views. Workflow changes go through typed KBD CLI, MCP or REST operations; runtime-generated projections are not edited directly ( installed KBD contract ).

 2.2 Nested loops 
 Phase Assess the situation, investigate options, specify and plan work, execute accepted changes, then reflect. 
 Change Execute bounded tasks, collect the required evidence, evaluate and record the result. 
 Artifact Refine a particular design, document, implementation or assessment against its own criteria. 
 Fig. 2 · Three nested loops, one shape Expand 
 FIG. 2 A worker owns an assignment at one level. It can propose work at another level through an artifact or command request, but it does not silently rewrite the parent goal. Use the deployed runtime’s schema for parent/child fields. 
Nested phases need explicit parent/child identity and revision-aware progress aggregation. Do not assume field spelling from one port is a portable schema: use the deployed runtime’s schema and adapter. 
 2.3 Four completion dimensions 
 Primary count · Executor Implementation Is the requested code or artifact and its integration contract implemented? 
 Tester or specialist Evidence Has the required verification evidence been collected? 
 Evaluators · approvers Certification Have the configured acceptance/authorization gates been satisfied? 
 Delivery role Publication Has the accepted result been delivered to its intended environment? 
The current KBD contract keeps implementation as the primary completed/total count. Pending evidence, authorization, elapsed-time, external-review or publication gates do not automatically reopen completed implementation. They can still prevent release. A subsequently discovered defect is recorded and handled according to the change policy rather than hidden by manipulating counts ( completion invariant ). 
 “Certification” is a workflow dimension. It does not mean HIPAA certification, CMMC certification, a banking regulator’s approval, or a qualified assessor’s attestation. 
 2.4 Concurrency and worktrees 
The installed KBD handoff contract describes an exclusive journal lock over the whole read/validate/append transaction and rejection of stale expected revisions. Atomic replacement of a JSON file is not equivalent to that transaction. Git commits are useful snapshots, but do not provide live mutual exclusion ( KBD transaction boundary ). 
For parallel code changes, use separate worktrees and explicit ownership. Prefer one designated KBD control-plane writer receiving revision-bound worker reports until a shared-runtime deployment has been verified. 
 Provides 
Exclusive lock over read → validate → append 
Stale expected revisions rejected 
Separate worktree per parallel change 
 Does not provide 
Atomic JSON replace ≠ a transaction 
Git commits ≠ live mutual exclusion 
A worktree ≠ a sandbox 
A worktree is still writable filesystem content; it is not a sandbox. Path restrictions require actual host enforcement. The installed child-scope hook is advisory by default, so its allowed paths must not be represented as a hard security boundary ( scope hook ). 
 2.5 Hooks and observer agents 
Hooks announce lifecycle boundaries and support telemetry, notifications and follow-up work. An observer may request a new assessment or propose a blocker, but the runtime admits any resulting transition under its normal authorization and revision rules. 
 A hook log is not automatically a durable delivery queue. An observer that must recover missed events needs a subscription, cursor, retention policy and acknowledged work record. Section B.4 describes the proposed event contract. 
 2.6 Startup and recovery 
A dispatched worker should: 
 Establish identity Project, worktree, principal and assigned task. 
 Load context Relevant project instructions and phase artifacts. 
 Confirm position Read the waypoint, then confirm authoritative runtime status and revision. 
 Load skills + grants The required skill revisions and tool grants. 
 Execute The assigned bounded work. 
 Return a report Artifacts, evidence, unresolved outcomes and a requested transition. 
 Let the writer record The authorized runtime writer records the accepted result. 
A graceful handoff includes the last completed work, exact next work, decisions, blockers, dirty state and plan revision. A receiving worker validates that checkpoint before continuing. After an ungraceful interruption, reconcile repository state, active processes and external action receipts first ( resume and handoff contract ). 
 PART III 
Roles, skills, and agent definitions 
 3.1 Keep role, skill, tool, harness and instance distinct 
 Concept Meaning 
 Role Responsibility, expected outputs and decision rights 
 Skill Reusable procedure and supporting knowledge/resources 
 Tool or connector Mechanism that reads or changes a system 
 Harness / runtime Execution, model/tool loop, permissions and lifecycle 
 Agent definition Versioned configuration combining a role with selected skills and policies 
 Agent instance A particular authorized identity with its own scope and optional state 
 Task / turn One bounded execution of an assignment 
 Fig. 12 · Seven concepts that must stay distinct Expand 
 FIG. 12 One developer may use several roles sequentially; several developers may share a pool of the same definitions with distinct project, tenant and task scopes. 
Agent Skills is the format at agentskills.io . The directory requested as “skill.sh” is skills.sh . They serve different purposes: the former specifies skill packaging; the latter helps discover and install skills. A directory listing is not an assurance of suitability or security. 
The format supports metadata such as name, description, compatibility and license, with optional supporting files. Its experimental allowed-tools field is not a universal enforcement mechanism — the host still owns effective permissions. A skill does not supply credentials, an event subscription, a daemon or a compliance certification. 
 3.2 Core lifecycle roles 
The supplied taxonomy enumerates nine useful core roles, despite describing them as six; they are retained below ( original document ). 
 Role Responsibility Main output 
 Orchestrator Select admitted work, dispatch, gate and record transitions Dispatches and accepted runtime transitions 
 Assessor Compare current state with goals Assessment and gaps 
 Analyst Investigate alternatives, dependencies and evidence Analysis and candidate evaluation 
 Planner / spec-writer Define acceptance criteria, interfaces and bounded tasks Specifications and change plan 
 Executor Implement authorized work in its assigned scope Patch or artifact and self-check evidence 
 Evaluator Independently judge a specified revision Findings and PASS / CONTINUE / BLOCK as configured 
 Tester Collect reproducible verification evidence Test results, traces, screenshots and environment details 
 Debugger / triage Classify and diagnose incoming failures Reproduction, diagnosis and routing recommendation 
 Delivery Engineer delivery infrastructure and operate authorized promotion Deployment/publication records and rollout evidence 
A tester may need an isolated output directory for screenshots and logs even when source is read-only. If test authoring is required, assign it as implementation work; do not let an evidence-only tester silently change the subject being tested. 
Likewise, pipeline engineering is an implementation assignment. Release operation is a separate authorized action. The same role definition can support both through different grants and fresh assignments. 
 3.3 Specialist roles supplement the lifecycle 
The six roles in Addendum A apply expertise across lifecycle stages. A UI designer may contribute to analysis, specification and evaluation. A Security Officer may assess a threat model, define security criteria and review release evidence. They do not each need their own independent project orchestrator.

Skill selection should be task-driven. Load the procedure needed for the current assignment, not every skill associated with a job title. A Product Manager writing a PRD needs specification and research-synthesis skills; it does not automatically need customer-message sending or Jira administration. 
 3.5 Write and decision ownership 
Every artifact or external resource needs a designated owner and conflict policy. Shared visibility does not mean unrestricted writes. 
 Product Problem statements and prioritization recommendations; accepted scope changes follow project governance. 
 Design Approved interaction and visual specifications. 
 Executors Patches for assigned implementation tasks. 
 Reviewers Findings — not silent repairs. 
 Documentation Designated pages and links; Product may own roadmap fields on the same Jira project. 
 Delivery Release permissions granted by the project, including standing authorization and protected-environment gates. 
 Approval is a policy, not a blanket rule. The original’s rule that every action beyond staging needs a fresh human approval is better expressed as an explicit project policy. An existing authorization may already cover a routine action. Where approval is required, prepare the concrete release package first, then stop at that boundary.

 In-harness delegation The coordinator dispatches role workers using native facilities. KBD remains the workflow authority. 
 Adapter / headless dispatch The coordinator starts a bounded invocation through a verified adapter. The adapter normalizes task identity, outputs, tool policy, cancellation, timeouts and errors.

A worker returns a report bound to the revision it started from:

 Fig. 7 · A revision-bound handoff Expand 
 FIG. 7 The dispatcher validates before it submits; the runtime rejects stale expected revisions inside one locked transaction. A stale report is reconciled — it never overwrites newer state. 
When transferring execution, the current writer checkpoints and stops issuing commands. The receiver establishes its own session/device identity, verifies runtime status and resumes under the supported contract. Preserve operator pause and cancellation. 
 5.2 KBD and the wider product architecture 
The recommended integration model, consistent with the preceding architecture assessment:

 FIG. 9 Recommended integration model. A UI can administer several local or remote instances without owning their model loops; persistent subscriptions do not require permanently resident model processes.

 Use one execution owner for each turn. A BossFang workflow can invoke a UAR agent through a full runtime adapter; a provider-only integration is not the same delegation boundary. A UI can administer several local or remote instances without owning their model loops. 
Specialists and feedback monitors can run as request-scoped workers or stateful logical instances. Persistent subscriptions and cursors do not require permanently resident model processes. These are proposed integration contracts, not a claim that all cross-product wiring already exists ( prior UAR/observer assessment ).

 ADDENDUM B 
Customer feedback, enhancement issues, and observer agents 
 B.1 Customer Feedback Analyst 
This role watches authorized support tickets, feedback forms, customer conversations, issue discussions, app feedback or product signals. It groups related observations and produces evidence-backed opportunities. 
It distinguishes a defect , usability problem , documentation gap , feature request , security report and contractual issue . Customer messages are untrusted task data, not instructions to change agent policy or reveal internal information. 
 Outputs Normalized feedback records, recurring themes, impact evidence, confidence/uncertainty and routing recommendations. Preserve evidence from one customer without pretending it represents many — and do not dismiss a serious single report merely because it is uncommon. 
 Skills ticket-triage , customer-research , user-research-synthesis , response-drafting and escalation , selected by task. Replying to a customer is optional and separately authorized. 
 State Cursors, source identities, deduplication keys, issue links and bounded topic summaries. Avoid retaining full conversations in every agent’s private history. 
 B.2 Enhancement Issue Curator 
Converts qualified opportunities into reviewable GitHub issues or updates an existing issue. It can be a separate agent, or a distinct assignment of the Feedback Analyst with a stronger grant. 
 01 
 Observe Internal feedback record and recommendation. 
 02 
 Draft Complete issue proposal awaiting admission. 
 03 
 Authorized automatic intake Create or update an issue in allowlisted repositories under standing policy. 
 04 
 Product commitment Prioritize, promise or schedule work only within separately delegated authority. 
 Automatic intake is a valid mode. It should not require a person to approve every ordinary issue once the policy is authorized. The policy defines repositories, visibility, allowed fields/labels, content restrictions, deduplication, rate limits and escalation cases. 
Creating an issue must not by itself authorize implementation. The planner admits accepted work into KBD, and the runtime records that decision.

Grouping requires evidence and may be revised; a similarity score is not proof that two problems are identical. 
An idempotency key in an issue body alone is insufficient. If the request times out, reconcile the remote result before retrying; search can lag, so uncertain cases may need a paused reconciliation state (Fig. 8). Serialize or coordinate competing writers for the same opportunity. 
GitHub documents issue creation, relevant token permissions and secondary rate limiting. Use a scoped application/credential and host policy rather than a general-purpose credential in model context. Do not assume a generic create-issue call is exactly-once ( GitHub issue API ). 
 Public issues are public. Bodies must not expose private customer transcripts, ePHI, CUI, credentials or private-support links that reveal identities. Private evidence stays in its authorized store behind a sanitized public summary. Security reports route to the designated confidential process.

 Fig. 11 · Subscription semantics Expand 
Within UAR 
Across BossFang channels FIG. 11 Each independent observer needs its own progress; a shared worker queue merely divides work among consumers. Observation alone does not make every subscriber answer. 
 Within UAR Committed events are matched to authorized subscriptions and admitted into each observer’s own work stream. The monitor gets a bounded turn under its own authority; it does not inherit the producer’s tools or approval context. 
 Across BossFang channels BossFang owns the channel source and primary routing. A feedback observer receives authorized copies. A separate handler subscription can make a Product Manager or support agent the primary respondent, but observation alone does not make every subscriber answer. 
 Across hosts Source-side permission to disclose and recipient-side permission to execute are both required. Fabric may transport events. The Boss displays subscription scope, placement, lag, delivery failures and permitted actions. 
Replay should be observe-only by default, with catch-up actions explicitly authorized. Preserve causation, suppress provider echoes, bound reaction depth and cost, and avoid starting another loop from the agent’s own issue-created notification ( observer architecture assessment ).

 Boundary. Standards come from the repository’s agreed rules and relevant platform constraints; a generic skill’s stylistic preference does not override the project. The reviewer does not patch, merge, waive branch protection or approve its own authored change under the same assignment. 
 Acceptance. Material findings are evidenced; speculative preferences are distinguished from blockers; automated checks and manual reasoning complement each other. A successful linter run is not the whole review.
